# Git 이해하기

미래패스의 모든 코드는 **Git**으로 관리하고, **GitHub**에 올려 함께 작업합니다.<br />
개발에 참여하려면 Git이 무엇인지 알아야 합니다. 설치 방법은 [Git 설치 가이드](/docs/install-git)를 확인하세요.

## 왜 Git이 필요할까?

과제나 보고서를 쓰다가 파일 이름이 이렇게 된 적 있나요?

```
보고서.hwp
보고서_수정.hwp
보고서_최종.hwp
보고서_최종_진짜최종.hwp
보고서_최종_진짜최종_선생님확인후.hwp
```

이렇게 관리하면 금방 문제가 생깁니다.

- 어느 파일이 진짜 최신인지 헷갈립니다.
- "어제 지운 문단을 다시 살리고 싶은데" 어느 파일에 있었는지 찾기 어렵습니다.
- 친구와 나눠서 쓰면, 서로 고친 내용을 하나로 합치는 데 시간이 오래 걸리고 실수로 덮어쓰기도 합니다.

미래패스는 수백 개의 파일로 이루어져 있고, 여러 사람이 동시에 고칩니다. 파일 이름을 바꿔 가며 관리하는 건 불가능합니다.

**Git은 파일이 언제, 누가, 무엇을, 왜 바꿨는지 모두 기록해 두고, 여러 사람이 고친 내용을 하나로 합칠 수 있게 해 주는 도구입니다.**<br />
이런 도구를 **버전 관리 시스템**이라고 합니다.

## 게임의 세이브 포인트

Git을 이해하는 가장 쉬운 방법은 **게임의 저장(세이브) 기능**을 떠올리는 것입니다.

- 보스를 잡기 전에 저장해 두면, 지더라도 저장한 곳에서 다시 시작할 수 있습니다.
- 저장 슬롯마다 "2층 보스 앞", "아이템 다 모음" 같은 이름을 붙여 두면 나중에 찾기 쉽습니다.

Git도 같습니다. 코드를 고치다가 적당한 때에 **저장 지점**을 만들어 둡니다.
코드가 망가지면 예전 저장 지점으로 돌아갈 수 있고, 각 저장 지점에 남긴 메모로 무엇을 바꿨는지 알 수 있습니다.

| 게임 | Git |
| --- | --- |
| 저장 슬롯 | **커밋(Commit)** |
| 저장 슬롯 이름 | **커밋 메시지** |
| 이전 저장으로 불러오기 | 예전 커밋으로 되돌리기 |
| 다른 루트를 따로 플레이해 보기 | **브랜치(Branch)** |

## 핵심 용어

### 저장소 (Repository) — 기록이 붙은 프로젝트 폴더 [#repository]

**저장소**는 Git이 관리하는 **프로젝트 폴더**입니다. 줄여서 **레포(repo)** 라고도 부릅니다.

겉보기에는 평범한 폴더지만, 안에 숨겨진 `.git` 폴더가 있어서 지금까지의 모든 변경 기록이 여기에 저장됩니다.
미래패스 코드가 들어 있는 `MIRAE-PASS` 폴더가 하나의 저장소입니다.

<Callout type="warning">
    `.git` 폴더를 지우면 모든 변경 기록이 사라집니다. 직접 열거나 수정하지 마세요.
</Callout>

### 커밋 (Commit) — 저장 지점 [#commit]

**커밋**은 "지금 이 순간 파일들의 상태"를 기록한 **저장 지점**입니다. 사진을 찍어 앨범에 붙여 두는 것과 비슷합니다.

커밋마다 아래 내용이 함께 기록됩니다.

- 누가 했는지 (이름, 이메일)
- 언제 했는지
- 무엇을 바꿨는지 (어느 파일의 몇 번째 줄이 어떻게 바뀌었는지)
- 왜 바꿨는지 (**커밋 메시지**)

```text
feat(client): 노래방 파티 초대 화면 추가
fix(server): stamp iso포멧에 맞지 않는 문제 해결
```

미래패스는 커밋 메시지를 정해진 형식으로 씁니다. 자세한 규칙은 [커밋 메시지 컨벤션](/docs/development/convention#커밋-메시지)을 확인하세요.

### 스테이징 (Staging) — 택배 상자에 담기 [#staging]

파일을 여러 개 고쳤더라도, 그중 **일부만 골라서** 커밋할 수 있습니다. 커밋할 파일을 고르는 것을 **스테이징**이라고 합니다.

택배를 보내는 과정으로 생각하면 쉽습니다.

| 택배 | Git |
| --- | --- |
| 보낼 물건을 상자에 담는다 | `git add` 로 커밋할 파일을 고른다 (스테이징) |
| 상자를 테이프로 봉하고 송장을 붙인다 | `git commit` 으로 커밋을 만들고 메시지를 적는다 |

### 브랜치 (Branch) — 평행 세계 [#branch]

**브랜치**는 원래 코드를 건드리지 않고 **따로 작업할 수 있는 공간**입니다. 영어로 "나뭇가지"라는 뜻입니다.

새 기능을 만들다가 코드가 망가지면, 다른 사람들도 모두 영향을 받습니다.
그래서 원래 코드에서 **가지를 하나 뻗어** 그 안에서 마음껏 작업하고, 완성되면 원래 가지에 **합칩니다(merge)**.

```
dev        ──●──────●──────────────●──▶   (합쳐진 결과)
               \                  /
feat/stamp      ●────●────●──────      (새 기능 작업)
```

미래패스는 아래와 같이 브랜치를 나눠서 사용합니다.

| 브랜치 | 용도 |
| --- | --- |
| `master` | 실제 학교에서 사용하는 정식 버전 |
| `dev` | 개발 중인 기능을 모아 두는 곳 |
| `feat/*`, `fix/*`, `docs/*` | 각자 작업하는 곳. 작업이 끝나면 `dev`에 합칩니다. |

자세한 내용은 [브랜치 컨벤션](/docs/development/convention#브랜치)을 확인하세요.

## Git과 GitHub는 다릅니다

이름이 비슷해서 헷갈리지만 둘은 다른 것입니다.

| | Git | GitHub |
| --- | --- | --- |
| 무엇인가 | 내 컴퓨터에 설치하는 **프로그램** | 저장소를 올려 두는 **웹사이트** |
| 비유 | 사진을 찍는 **카메라** | 사진을 올려 공유하는 **온라인 앨범** |
| 인터넷 | 없어도 사용 가능 | 필요 |

Git만 있으면 내 컴퓨터 안에서 기록을 남길 수 있습니다.
여러 사람이 함께 작업하려면 모두가 접속할 수 있는 곳에 저장소를 올려 두어야 하는데, 이 역할을 [GitHub](https://github.com)가 합니다.
미래패스 저장소는 [github.com/scfs-miraepass/MIRAE-PASS](https://github.com/scfs-miraepass/MIRAE-PASS)에 있습니다.

### 원격 저장소와 로컬 저장소 [#remote]

- **원격 저장소(Remote)**: GitHub에 올라가 있는 저장소. 모두가 함께 보는 원본입니다.
- **로컬 저장소(Local)**: 내 컴퓨터로 복사해 온 저장소. 내가 실제로 코드를 고치는 곳입니다.

둘 사이에서 내용을 주고받는 명령어는 세 가지입니다.

| 명령어 | 하는 일 | 비유 |
| --- | --- | --- |
| `git clone` | 원격 저장소를 내 컴퓨터로 **처음 통째로 복사**합니다. | 공유 앨범 전체를 내려받기 |
| `git pull` | 원격 저장소에 새로 올라온 커밋을 **내려받아** 내 저장소에 반영합니다. | 친구가 새로 올린 사진 받기 |
| `git push` | 내가 만든 커밋을 원격 저장소로 **올립니다**. | 내가 찍은 사진 올리기 |

```
            GitHub (원격 저장소)
             ▲              │
   git push  │              │  git clone / git pull
             │              ▼
            내 컴퓨터 (로컬 저장소)
```

<Callout type="info">
    `git commit` 은 **내 컴퓨터에만** 저장됩니다. `git push` 를 해야 GitHub에 올라가고 다른 사람이 볼 수 있습니다.
</Callout>

### Pull Request — 합쳐 달라는 요청 [#pull-request]

내 브랜치에서 작업을 마쳤다고 바로 `dev`에 합치지 않습니다. 다른 사람이 먼저 코드를 **검토(리뷰)** 해야 합니다.

**Pull Request(PR)** 는 GitHub에서 **"제 브랜치의 작업을 `dev`에 합쳐 주세요"** 라고 요청하는 글입니다.
조별 과제에서 내가 맡은 부분을 조장에게 보내 확인받는 것과 비슷합니다.

- 무엇을 왜 바꿨는지 PR에 적습니다.
- 검토하는 사람은 바뀐 코드를 한 줄씩 보며 의견을 남깁니다.
- 문제가 없으면 검토한 사람이 **머지(merge)** 버튼을 눌러 합칩니다.

## 미래패스에서 작업하는 흐름

<Steps>

### 저장소 복사하기 (처음 한 번)

GitHub의 미래패스 저장소를 내 컴퓨터로 복사합니다.

```bash
git clone https://github.com/scfs-miraepass/MIRAE-PASS.git
cd MIRAE-PASS
```

### 최신 코드 받기

작업을 시작하기 전에 `dev` 브랜치로 이동해 다른 사람이 올린 최신 코드를 받습니다.

```bash
git switch dev
git pull
```

### 작업용 브랜치 만들기

`dev`에서 내 작업용 브랜치를 만들고 그 브랜치로 이동합니다. 이름은 [브랜치 컨벤션](/docs/development/convention#브랜치)에 맞춰 짓습니다.

```bash
git switch -c feat/stamp-history
```

### 코드를 고치고 커밋하기

코드를 고친 뒤, 커밋할 파일을 고르고(스테이징) 커밋합니다. 작업 중에 여러 번 커밋해도 됩니다.

```bash
git status                                     # 바뀐 파일 확인하기
git add client/app/pages/stamp.vue             # 커밋할 파일 고르기
git commit -m "feat(client): 스탬프 내역 화면 추가"   # 커밋하기
```

### GitHub에 올리기

내 브랜치를 GitHub에 올립니다. 처음 올릴 때는 `-u origin 브랜치이름` 을 붙입니다.

```bash
git push -u origin feat/stamp-history
```

### Pull Request 만들기

GitHub 저장소 페이지에 들어가면 **Compare & pull request** 버튼이 보입니다. 눌러서 `dev`로 합쳐 달라는 PR을 만듭니다.

### 검토 후 합치기

검토하는 사람이 코드를 확인하고 `dev`에 합칩니다. 수정 요청이 오면 같은 브랜치에서 고치고 다시 커밋·push하면 PR에 자동으로 반영됩니다.

</Steps>

<Callout type="warning">
    `master`와 `dev`에는 직접 push하지 않습니다. 두 브랜치에 push되면 새 버전이 자동으로 만들어집니다. ([배포](/docs/development/deploy) 참고)
</Callout>

## 자주 쓰는 명령어

저장소 폴더(`MIRAE-PASS`) 안에서 실행합니다.

| 명령어 | 하는 일 |
| --- | --- |
| `git status` | 지금 어느 브랜치에 있는지, 어떤 파일이 바뀌었는지 보기 |
| `git diff` | 아직 커밋하지 않은 변경 내용을 줄 단위로 보기 |
| `git log --oneline` | 지금까지의 커밋 목록을 한 줄씩 보기 (`q`로 나가기) |
| `git switch 브랜치이름` | 다른 브랜치로 이동하기 |
| `git switch -c 브랜치이름` | 새 브랜치를 만들고 이동하기 |
| `git add 파일` | 커밋할 파일 고르기 (스테이징) |
| `git commit -m "메시지"` | 고른 파일로 커밋 만들기 |
| `git pull` | 원격 저장소의 새 커밋 받기 |
| `git push` | 내 커밋을 원격 저장소에 올리기 |

<Callout type="info">
    명령어 대신 버튼으로 Git을 다루고 싶다면 [GitHub Desktop](https://desktop.github.com)이나 VS Code, WebStorm 같은 편집기에 들어 있는 Git 기능을 사용할 수도 있습니다. 하는 일은 위 명령어와 같습니다.
</Callout>

### Git은 기록하는 프로그램

파일이 언제, 누가, 무엇을, 왜 바꿨는지 **커밋**으로 기록합니다.

원래 코드를 건드리지 않도록 **브랜치**를 만들어 그 안에서 작업합니다.

내 커밋을 GitHub에 **push**하고, **Pull Request**로 검토를 받은 뒤 `dev`에 합칩니다.

</Steps>
