# 배포

미래패스는 GitHub Actions가 버전을 정하고 Docker 이미지를 빌드해 올립니다.<br />
사람이 할 일은 **릴리스 PR 만들기 버튼을 누르고, 그 PR을 머지하는 것**뿐입니다. 나머지는 자동으로 진행됩니다.

## 릴리스 흐름

`master` 또는 `dev` 브랜치에 push하면 [`release.yml`](https://github.com/scfs-miraepass/MIRAE-PASS/blob/master/.github/workflows/release.yml)가 실행됩니다.

1. **버전 결정**: [semantic-release](https://semantic-release.gitbook.io)가 커밋 메시지([Conventional Commits](https://www.conventionalcommits.org/ko/v1.0.0/))를 읽고 다음 버전을 정합니다.
   - `feat` → Minor, `fix`·`perf` → Patch, `BREAKING CHANGE` → Major
   - 릴리스할 커밋이 없으면 여기서 끝나고 이미지도 빌드하지 않습니다.
2. **버전 반영**: `client`, `admin`, `server`의 버전을 한 번에 올리고 `CHANGELOG.md`와 함께 `chore(release): x.y.z [skip ci]` 커밋과 `vx.y.z` 태그를 만듭니다.
3. **이미지 빌드**: 새 태그를 기준으로 세 이미지를 빌드해 GitHub Container Registry에 올립니다.
4. **dev 동기화** (`master`만): 릴리스가 끝나면 [`sync-dev.yml`](https://github.com/scfs-miraepass/MIRAE-PASS/blob/master/.github/workflows/sync-dev.yml)이 `master`의 릴리스 커밋을 `dev`에 반영합니다. ([dev 동기화](#dev-동기화) 참고)

`dev`에 push하면 `x.y.z-dev.n` 프리릴리스가, `master`에 push하면 정식 릴리스가 만들어집니다.

## 정식 릴리스 하기

`dev`에 모인 변경 사항을 `master`로 보내 정식 릴리스를 만듭니다.

<Steps>

### 릴리스 PR 만들기

GitHub의 **Actions → Release PR → Run workflow**를 누릅니다.<br />
[`release-pr.yml`](https://github.com/scfs-miraepass/MIRAE-PASS/blob/master/.github/workflows/release-pr.yml)이 `dev` → `master` PR을 만들고, 본문에 예상 버전과 변경 목록을 적습니다.
이미 열려 있는 릴리스 PR이 있으면 새로 만들지 않고 제목과 본문을 최신 내용으로 갱신합니다.

### 내용 확인하기

PR 본문의 **예상 다음 버전**과 **변경 사항**이 의도한 것과 맞는지 확인합니다.<br />
예상 버전은 커밋 type으로 계산한 값이며, 실제 버전은 머지 후 semantic-release가 정합니다.

### 머지하기

**Create a merge commit**으로 머지합니다.

<Callout type="warning">
    **Squash and merge**나 **Rebase and merge**를 쓰지 않습니다.<br />
    Squash하면 커밋 type이 PR 제목 하나로 합쳐져 버전이 잘못 정해지고, 두 방식 모두 `dev`와 `master`의 기록이 달라져 [dev 동기화](#dev-동기화)가 충돌할 수 있습니다.
</Callout>

### 끝

정식 릴리스와 이미지 배포가 진행되고, 이어서 `dev`가 자동으로 `master`와 맞춰집니다. 따로 할 일은 없습니다.

</Steps>

## dev 동기화

정식 릴리스를 하면 `master`에만 릴리스 커밋(`chore(release): x.y.z [skip ci]`)이 생깁니다.
이 커밋을 `dev`에 반영하지 않으면 다음 릴리스에서 두 브랜치의 기록이 어긋나므로, `sync-dev.yml`이 자동으로 반영합니다.

`master`에서 **Docker Image Release** 또는 **Docs Deploy** 워크플로가 끝나면 실행되며, 상황에 따라 다르게 동작합니다.

| 상황 | 동작 |
| --- | --- |
| `dev`에 이미 반영되어 있음 | 아무것도 하지 않습니다. |
| `dev`에 새 커밋이 없고, `master`의 마지막 커밋에 `[skip ci]`가 있음 | `dev`를 `master`로 fast-forward합니다. |
| 그 밖의 경우 (`dev`에 새 커밋이 있는 경우 등) | `chore: master 변경 사항을 dev에 반영 [skip ci]` merge 커밋을 만들어 push합니다. |
| 충돌 | `dev`를 바꾸지 않고, `[자동] master를 dev에 반영하지 못했습니다` 이슈를 만듭니다. |

push하는 커밋에는 항상 `[skip ci]`가 붙어 있어, 동기화 때문에 `dev` 프리릴리스가 만들어지지 않습니다.<br />
동기화는 **Actions → Sync dev → Run workflow**로 직접 실행할 수도 있습니다.

### 충돌이 난 경우

릴리스 직후 `dev`에 다른 프리릴리스가 먼저 올라간 경우처럼, 두 브랜치가 같은 파일을 바꿨다면 충돌이 날 수 있습니다.
저장소 관리자가 아래 순서로 직접 반영합니다. (`dev`에 직접 push하는 권한이 필요합니다.)

```bash
git fetch origin
git switch dev
git pull
git merge origin/master
# 충돌한 파일을 고친 뒤
git add .
git commit -m "chore: master 변경 사항을 dev에 반영 [skip ci]"
git push origin dev
```

- 버전 파일(`client/package.json`, `admin/package.json`, `server/pyproject.toml`, `server/uv.lock`)의 버전 충돌은 어느 쪽을 골라도 됩니다. 다음 릴리스에서 semantic-release가 다시 정합니다.
- `CHANGELOG.md`는 양쪽 내용을 모두 남깁니다.
- 반영한 뒤 이슈를 닫습니다.

## 이미지와 태그

| 이미지 |
| --- |
| `ghcr.io/scfs-miraepass/mirae-pass/client` |
| `ghcr.io/scfs-miraepass/mirae-pass/admin` |
| `ghcr.io/scfs-miraepass/mirae-pass/server` |

| 태그 | 붙는 경우 |
| --- | --- |
| `x.y.z` | 모든 릴리스 (예: `1.14.1`, `1.15.0-dev.1`) |
| `latest` | `master` 브랜치 릴리스 |
| `dev` | `dev` 브랜치 릴리스 (프리릴리스 `x.y.z-dev.n`) |

운영용 `docker-compose.yml`은 `latest` 태그를 사용합니다.

## 수동 릴리스

semantic-release를 거치지 않고 원하는 버전으로 릴리스하려면 GitHub의 **Actions → Docker Image Release → Run workflow**에서 `manual_version`에 버전(예: `1.15.0`)을 입력합니다.
버전에 `-`가 들어가면(예: `1.15.0-rc.1`) 프리릴리스로 표시됩니다.

## 릴리스에 필요한 저장소 설정

릴리스 커밋을 보호된 브랜치에 push하고 릴리스 PR을 만들기 위해 GitHub App 토큰을 사용합니다. 저장소 **Settings → Secrets and variables → Actions**에 아래 값이 있어야 합니다.

| Secret | 내용 |
| --- | --- |
| `RELEASE_APP_ID` | 릴리스용 GitHub App의 App ID |
| `RELEASE_APP_PRIVATE_KEY` | 그 App의 Private key |

App은 저장소에 설치되어 있어야 하고, 아래 조건을 갖춰야 합니다.

| 조건 | 쓰는 곳 |
| --- | --- |
| 브랜치 보호 규칙 우회 | 릴리스 커밋 push, dev 동기화 |
| Contents: Read and write | 릴리스 커밋·태그 push, dev 동기화 |
| Pull requests: Read and write | 릴리스 PR 만들기 |

<Callout type="info">
    `sync-dev.yml`은 `workflow_run`으로 실행되기 때문에, 이 파일이 `master`에 있어야 동작합니다.
</Callout>
