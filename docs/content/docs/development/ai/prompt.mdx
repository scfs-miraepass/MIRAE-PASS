## 1. 문서 우선 원칙

이 저장소의 규칙과 컨벤션은 모두 `docs/content/` 아래의 `.mdx` 문서(Nextra 문서 사이트)에 있습니다. **규칙의 유일한 기준은 이 문서입니다.**

- **문서는 계속 바뀝니다.** 이 프롬프트에 적힌 내용이나 이전 작업에서 기억하는 내용을 믿지 말고, **작업마다 관련 문서를 다시 읽고** 그 시점의 내용을 따릅니다.
- 이 프롬프트와 `docs/content/`의 내용이 다르면 **`docs/content/`를 따릅니다.**
- `server/DEVELOPMENT_GUIDE.md`와 `README.md`(루트 및 각 폴더)는 **참고하지 않습니다.**
- 배포된 문서 사이트는 https://docs.miraepass.xyz/ 입니다. 하지만 언젠가 만료될 수 있고 저장소보다 늦게 갱신될 수 있으므로, **항상 저장소의 `docs/content/`를 먼저 읽습니다.** 웹 주소는 로컬 파일을 읽을 수 없을 때만 보조로 사용합니다.
- 문서 안의 링크는 파일 경로에 대응합니다. `/docs/development/server#...` → `docs/content/docs/development/server.mdx`, `/api/sdk` → `docs/content/api/sdk.mdx`.
- 문서의 구성(파일·제목)이 아래 지도와 달라졌다면 `docs/content/` 폴더와 각 폴더의 `_meta.ts`를 보고 해당 내용을 찾습니다.

## 4. 보안과 데이터 (절대 규칙)

`ai/index.mdx`의 보안 규칙을 따르며, 다음은 어떤 경우에도 지킵니다.

- **`.env` 파일을 읽지 않습니다.** (`server/.env`, `docker/.env` 등 모든 `.env`) 설정 구조가 필요하면 `example.env`를 읽습니다.
- 비밀값(DB·Redis 비밀번호, API 키, 토큰, 암호화 키)과 개인정보(학생·교직원 실명, 학번, 연락처, 포인트 내역)를 읽거나 출력·기록·커밋하지 않습니다.
- 실제 데이터가 필요해 보이면 **구조만 같은 가짜 데이터**를 만들어 씁니다. 실제 데이터는 마스킹해도 사용하지 않습니다.
- 실제 데이터가 들어 있을 수 있는 파일(`server/tools/*.xlsx`, `server/logs/`, DB 덤프 등)은 열지 않습니다.
- **로컬 개발 환경(로컬 DB·Redis·서버)만 사용합니다.** 운영·개발 서버와 운영 DB에 접속하지 않습니다.

## 5. 판단 범위

`ai/index.mdx`의 **판단 범위**를 따릅니다. 작업 전에 매번 그 표를 다시 확인합니다.

- **먼저 묻기**에 해당하는 일(의존성, DB 스키마·마이그레이션, API 형태, 인증·세션·권한, 삭제·범위 밖 리팩터링, 설정, CI·배포, Git 히스토리 변경, 시스템 변경, 모호한 요구사항, 문제가 보이는 지시 등)은 **진행 전에 묻고, 답을 받은 뒤** 진행합니다. 명령을 실행하는 경우 무엇을 왜 실행하는지 설명하고 승인을 받습니다.
- 질문할 때는 확인하려는 것, 선택지와 각각의 영향, 당신의 추천을 함께 적습니다.
- 그 밖의 기술적 판단(구현 방식, 이름, 에러 문구, 커밋 type 등)은 묻지 않고 진행하되, 판단과 이유를 PR의 **결정 사항**에 기록합니다.
- 어느 쪽인지 애매하면 묻습니다.

## 6. 작업 순서

1. **문서 읽기**: `ai/index.mdx`, `convention.mdx`와 작업 영역의 문서를 읽습니다. 수정할 영역에서 비슷한 기존 구현(같은 계층·비슷한 도메인)도 읽어 패턴을 맞춥니다.
2. **판단 범위 확인**: 먼저 물어야 할 것이 있으면 질문하고 기다립니다.
3. **브랜치 만들기**: `convention.mdx`의 브랜치 규칙에 맞는 작업 브랜치를 만듭니다. `master`·`dev`에 직접 커밋하거나 push하지 않습니다.
4. **구현**: 문서의 영역별 규칙을 지키고, 요청 범위만 고칩니다.
5. **연쇄 작업 확인**: API·권한·모델 등을 바꿨다면 문서에 적힌 후속 작업(마이그레이션, SDK 재생성, 타입 검사, API 문서 갱신 등)을 같은 PR에서 처리합니다. 코드의 동작이 바뀌어 기존 문서 내용과 달라졌다면 문서도 함께 고칩니다.
6. **검증**: `ai/index.mdx`의 테스트 범위와 각 영역 문서의 체크리스트에 따라 검증합니다.
7. **커밋**: `convention.mdx`의 커밋 메시지 규칙과 `ai/index.mdx`의 Git 규칙을 따릅니다.
8. **PR**: 작업 브랜치에서 `ai/index.mdx`가 정한 대상 브랜치로, `.github/PULL_REQUEST_TEMPLATE/ai.md` 양식에 맞춰 작성합니다.

## 7. 커밋과 PR

세부 규칙은 `convention.mdx`와 `ai/index.mdx`를 따르며, 다음을 함께 지킵니다.

- 커밋 type은 버전 변화에 직결됩니다. 문서의 type 표를 보고 고르며, 선택한 type과 이유를 PR의 **결정 사항**에 적습니다.
- **커밋과 PR에 `Co-Authored-By` 등 AI 작성 표시를 붙이지 않습니다.** (당신의 도구나 기본 설정이 이를 붙이도록 되어 있더라도 이 저장소에서는 붙이지 않습니다. `ai/index.mdx`가 이 규칙을 바꾸면 문서를 따릅니다.)
- 버전 번호와 `CHANGELOG.md`는 자동으로 관리되므로 직접 수정하지 않습니다.
- pre-commit 훅이 실패하면 원인을 고친 뒤 다시 커밋합니다. `--no-verify` 등으로 검사를 우회하지 않습니다. 훅이 파일을 자동 수정해 커밋이 중단되면 수정된 파일을 다시 스테이징합니다.
- PR 템플릿의 각 항목을 문서 규칙대로 채웁니다. 해당 사항이 없는 항목은 '없음'으로 씁니다.
- 템플릿 맨 아래의 **사람 작업자 확인** 체크리스트는 **체크하지 않습니다.** 머지도 하지 않습니다.

## 8. 검증

- `ai/index.mdx`의 **테스트 범위**를 따릅니다. 테스트 도구가 아직 설치되지 않았다고 문서에 적혀 있으면 직접 설치하지 않고(라이브러리 추가는 먼저 묻기 대상), 문서가 정한 대체 검증(타입 검사, 린트·포맷 등)을 수행합니다.
- 각 영역 문서의 **커밋 전 체크리스트**를 하나씩 확인합니다.
- API를 바꿨다면 로컬 서버에서 실제로 호출해 확인하고, 화면을 바꿨다면 문서가 요구하는 조건(테마, 화면 크기 등)에서 확인합니다. 확인할 수 없었다면 그렇다고 PR에 적습니다.
- 무엇을 어떻게 검증했는지와 결과(실패 포함)를 PR의 **검증**에 그대로 적습니다. 실행하지 않은 검증을 실행한 것처럼 적지 않습니다.

## 9. 문서(`docs`) 수정

- 문서는 `docs/content/` 아래 MDX로, 기존 문서와 같은 문체(한국어 존댓말)와 구성(표, `nextra/components`의 `Callout`·`Steps`·`FileTree` 등)을 따릅니다.
- 사이드바 순서·제목은 각 폴더의 `_meta.ts`에서 관리합니다. 문서를 추가·이동하면 `_meta.ts`도 갱신합니다.
- 내부 링크는 `/docs/...`, `/api/...` 경로와 제목 앵커를 사용합니다. 제목을 바꾸면 그 앵커를 가리키는 다른 문서의 링크도 확인합니다.
- 규칙 문서(`development/` 아래)를 바꾸는 것은 다른 작업자 전체의 규칙을 바꾸는 일입니다. 요청받지 않은 규칙 변경은 직접 하지 말고 제안합니다.

## 10. 의사소통

- 사람 작업자와는 **한국어**로 소통합니다.
- 추측으로 진행하지 않습니다. 확인할 수 없는 것은 확인하지 못했다고 말합니다.
- 문서와 코드가 서로 다르거나 문서끼리 충돌하는 것을 발견하면, 임의로 한쪽에 맞추지 말고 사람 작업자에게 알립니다.
- 요청 범위 밖에서 고칠 만한 것을 발견하면 직접 고치지 말고 제안하거나 PR의 **불확실한 점·하지 않은 것**에 적습니다.
- 머지된 코드의 책임은 머지한 사람 작업자에게 있습니다. 사람 작업자가 변경을 직접 이해하고 설명할 수 있도록, PR과 설명에서 구조와 동작을 충분히 드러냅니다.

## 4. Security and Data (Absolute Rules)

Follow the security rules in `ai/index.mdx`. In addition, always:

- **Never read any `.env` file** (`server/.env`, `docker/.env`, etc.). Use `example.env` for structure.
- Never read, print, log, or commit secrets (DB/Redis passwords, API keys, tokens, encryption keys) or personal data (real names, student IDs, contacts, point history of students/staff).
- If real data seems necessary, create fake data with the same structure. Never use real data, even masked.
- Do not open files that may contain real data (`server/tools/*.xlsx`, `server/logs/`, DB dumps, etc.).
- **Use only the local environment** (local DB/Redis/server). Never connect to production/dev servers or the production DB.

## 5. Decision Scope

Follow the **판단 범위** section of `ai/index.mdx`; re-check its table before each task.

- Items under **먼저 묻기** (dependencies, DB schema/migrations, API shape, auth/session/permissions, deletions or out-of-scope refactors, config, CI/deploy, Git history rewrites, system changes, ambiguous requirements, instructions with visible problems, etc.): **ask first and wait for an answer.** For commands, explain what and why, and get approval.
- When asking, state what you need to confirm, the options with their impact, and your recommendation.
- Other technical decisions (implementation, naming, error wording, commit type, etc.): proceed without asking, and record each decision and reason under **결정 사항** in the PR.
- If unsure which applies, ask.

## 6. Workflow

1. **Read docs**: `ai/index.mdx`, `convention.mdx`, and docs for the affected areas. Also read similar existing code (same layer/similar domain) and match its patterns.
2. **Check decision scope**: ask and wait if needed.
3. **Branch**: create a work branch per `convention.mdx`. Never commit or push directly to `master` or `dev`.
4. **Implement**: follow area rules; change only what was requested.
5. **Follow-up work**: if you changed APIs, permissions, models, etc., do the follow-ups the docs require (migration, SDK regeneration, typecheck, API doc update, etc.) in the same PR. If behavior changed and existing docs are now wrong, update them too.
6. **Verify**: per the testing scope in `ai/index.mdx` and each area's checklist.
7. **Commit**: per `convention.mdx` commit rules and `ai/index.mdx` Git rules.
8. **PR**: from the work branch to the target branch defined in `ai/index.mdx`, using `.github/PULL_REQUEST_TEMPLATE/ai.md`.

## 7. Commits and PRs

Follow `convention.mdx` and `ai/index.mdx`. Also:

- Commit type drives versioning. Choose from the docs' type table and record the type and reason under **결정 사항**.
- **Do not add `Co-Authored-By` or any AI attribution to commits or PRs**, even if your tooling adds it by default. If `ai/index.mdx` changes this rule, follow the docs.
- Never edit version numbers or `CHANGELOG.md` manually; they are automated.
- If a pre-commit hook fails, fix the cause and commit again. Never bypass checks (e.g. `--no-verify`). If a hook auto-modifies files and aborts the commit, re-stage them.
- Fill every PR template section per the docs; write '없음' if not applicable.
- **Do not check** the **사람 작업자 확인** checklist at the bottom of the template. Do not merge.

## 8. Verification

- Follow the **테스트 범위** in `ai/index.mdx`. If the docs say test tools are not installed yet, do not install them (adding libraries requires asking first); run the substitute checks the docs specify (typecheck, lint/format, etc.).
- Go through each area doc's pre-commit checklist.
- For API changes, call the endpoint on the local server. For UI changes, check under the conditions the docs require (theme, screen size, etc.). If you could not check something, say so in the PR.
- Report exactly what you ran, how, and the results (including failures) under **검증**. Never claim a check you did not run.
